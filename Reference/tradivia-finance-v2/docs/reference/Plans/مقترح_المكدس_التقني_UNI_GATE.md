# مقترح المكدس التقني لمنصة UNI GATE

## 1. توضيح الأسماء

| الاسم | المعنى |
|-------|--------|
| **UNI GATE** | شركتنا — اسم المنصة والمنتج الذي نبنيه ونبيعه |
| **TRADIVIA** | عميل حالي — استلم النسخة التجريبية من **نظام المالية** (حركة صناديق وسلف) المبني على Google Apps Script |
| **نظام الصرافة** | منتج/وحدة مستقلة حالياً — سيُدمج لاحقاً كقسم «صرافة» داخل UNI GATE |

هذه الوثيقة تصف **منصة UNI GATE** وليس نظام TRADIVIA وحده. نظام TRADIVIA هو أول عميل تجريبي يُهاجَر منه إلى المنصة الجديدة.

---

## 2. الصورة العامة — ماذا نبني؟

### 2.1 نوع المنتج

منصة **SaaS متعددة الشركات (Multi-Tenant)**:

- كل زبون = **شركة مستقلة** (مستخدمون، صلاحيات، بيانات، إعدادات).
- **المالية العامة** مفعّلة دائماً لكل شركة.
- **أقسام اختيارية** تُفتح حسب الاشتراك: صرافة، ذهب، طيران، هندسة، تجاري/مصانع، وغيرها.

### 2.2 أمثلة على الأقسام (وحدات)

| القسم | الوصف |
|-------|--------|
| مالية عامة | صناديق، وارد/صادر، تصريف، تحويل، سلف، موافقات، تقارير — **إلزامي** |
| صرافة | نظام الصرافة المستقل الحالي — يُدمج كوحدة |
| ذهب | محلات الذهب |
| طيران | مكاتب طيران |
| هندسة | مكاتب هندسية |
| تجاري / مصانع | شركات تجارية وصناعية |

الزبون يختار الأقسام التي يحتاجها؛ المالية تبقى مشتركة بينها جميعاً.

### 2.3 المبدأ المعماري

```
تطبيق واحد  +  قاعدة بيانات واحدة  +  لغة أساسية واحدة
        ↓
وحدات (Modules) داخل نفس المشروع
        ↓
عزل بيانات كل شركة عبر tenant_id (وليس نسخة Google Sheet لكل عميل)
```

**لا نبدأ بـ:** خدمات مصغّرة (Microservices)، ولا قاعدة بيانات لكل عميل، ولا Oracle من اليوم الأول.

## 3. المكدس التقني الموحّد (القرار المقترح)

| الطبقة | الاختيار | الدور |
|--------|----------|--------|
| لغة البرمجة | **TypeScript** | لغة موحّدة للواجهة والخادم |
| الواجهة | **React + Next.js** | تطبيق ويب (عربي/RTL، جداول، تقارير، طباعة) |

| ORM | **Prisma** | تعريف الجداول والاستعلامات بأمان |
| المصادقة | **JWT + Refresh Tokens** (أو Auth.js) | جلسات آمنة لكل شركة |
| المرفقات | **تخزين كائنات** (S3 / Cloudflare R2 / MinIO) | إيصالات ومرفقات بدل روابط Drive |
| الكاش (لاحقاً) | **Redis** | عند الحاجة — ليس في اليوم الأول |
| الاستضافة | VPS أو منصة سحابية + Postgres مُدار | تشغيل التطبيق والقاعدة |
| إدارة الكود | **Git** (GitHub / GitLab) | نسخ، مراجعة، نشر |
| CI/CD (لاحقاً) | GitHub Actions | نشر تلقائي بعد الاستقرار |
| مراقبة الأخطاء | **Sentry** | تتبع الأعطال في الإنتاج |
| النسخ الاحتياطي | نسخ يومي تلقائي لـ Postgres + تجربة استرجاع | حماية بيانات العملاء |

## 7. مقارنة تفصيلية — قاعدة البيانات

| المعيار | **PostgreSQL** | MySQL | SQLite | MongoDB | SQL Server / Oracle |
|---------|----------------|-------|--------|---------|---------------------|
| محاسبة وأرصدة | ممتاز | جيد | ضعيف للتزامن | غير مناسب كأساس | ممتاز |

| قيود البيانات (Integrity) | قوية جداً | جيدة | جيدة محلياً | ضعيفة | قوية |
| تزامن (موظفان يكتبان) | ممتاز | جيد | محدود | معقد | ممتاز |

## 9. مقارنة — البنية المعمارية

| النموذج | **Monolith مقسّم وحدات (مقترح)** | Microservices | نسخة لكل عميل (GAS) |
|---------|----------------------------------|---------------|---------------------|
| سرعة البداية | سريعة | بطيئة جداً | سريعة مؤقتاً |
| صيانة | متوسطة | معقدة جداً | كارثية عند التوسع |
| multi-tenant | طبيعي | معقد | غير مناسب |
| فريق 2 + AI | **مناسب** | غير مناسب | غير مناسب |

### هيكل مقترح للمشروع

```
uni-gate/
├── apps/
│   ├── web/          ← Next.js (الواجهة)
│   └── api/          ← NestJS (الخادم)
├── packages/
│   ├── database/     ← Prisma + مخطط PostgreSQL
│   └── shared/       ← أنواع مشتركة، ثوابت
└── modules/
    ├── finance/      ← المالية العامة (المرحلة 1)
    ├── exchange/     ← الصرافة (المرحلة 3)
    ├── gold/         ← لاحقاً
    └── ...
```

كل جدول تشغيلي يحمل `tenant_id` (معرّف الشركة) لعزل بيانات الزبائن.

## 11. خطة المراحل

| المرحلة | الهدف | المخرجات | ملاحظة |
|---------|--------|----------|--------|
| **0** | تثبيت القرار التقني | موافقة الإدارة + المبرمج، repo، مخطط جداول | أسبوع |
| **1** | هجرة **نظام المالية** (مثل ما يستخدمه TRADIVIA) | نفس الوظائف على Postgres + واجهة أسرع | **لا فواتير ولا قيود بعد** |
| **2** | محاسبة احترافية | فواتير بيع/شراء، قيود، أرباح، ميزانية، تقارير | فوق نفس القاعدة |
| **3** | دمج **نظام الصرافة** كوحدة في UNI GATE | قسم صرافة + مالية مشتركة | بعد استقرار المرحلة 1–2 |
| **4** | ERP كامل مع صديق المبرمج | وحدات إضافية حسب الطلب | ذهب، طيران، هندسة… |

**واقعياً لعميل يتوسع خلال شهر:** الهدف = **المرحلة 1** (نظام مستقر)، وليس محاسبة كاملة في نفس الشهر.

### ما لا نفعله على Google Sheets أثناء الانتقال

لا نضيف على الشيت/السكربت: فواتير، قيود يومية، ميزانية، أو وحدات محاسبية «مؤقتة» — أي يوم يُصرف هناك يؤخر الهجرة ويضاعف عمل النقل.

## 12. إصلاحات عاجلة على النسخة الحالية (Apps Script)

حتى اكتمال الهجرة، تُصلَح على GAS فقط **أعطال طارئة** للعملاء (مثل: حذف يمسح الصف، إشعارات فارغة، بحث متقدم). التحسينات الكبيرة تكون على UNI GATE.

## 13. المخاطر وإدارتها (فريق يعتمد AI)

| المخاطر | الإجراء |
|---------|---------|
| كود AI غير منظم | NestJS modules + مراجعة المبرغ لكل تغيير |
| أخطاء مالية | DB transactions + soft delete + اختبار أرصدة |
| تعدد الشركات | `tenant_id` من اليوم الأول |
| آلاف العملاء | فهرسة، أرشفة، Redis لاحقاً — **نفس Postgres** |
| فقدان بيانات | نسخ يومي + تجربة استرجاع شهرية |

---

## 14. ما نحتاج من الشريك المبرمج قبل البدء

1. الموافقة على **TypeScript + NestJS + PostgreSQL** (أو بديل **واحد** مبرر — لا خلط لغات بدون سبب).
2. تحديد المسؤوليات: مخطط DB، مراجعة كود، نشر، نسخ احتياطي.
3. الاتفاق على **multi-tenant** من اليوم الأول.
4. عدم بناء microservices في المرحلة الأولى.

---

## 15. القرار المختصر للإدارة (جملة واحدة)

> **UNI GATE منصة SaaS على TypeScript + Next.js + NestJS + PostgreSQL، متعددة الشركات، بوحدة مالية أولاً ثم محاسبة احترافية ثم دمج وحدات (صرافة، ذهب، طيران…) — مع هجرة عملاء مثل TRADIVIA من Google Apps Script دون الاعتماد على Sheets كقاعدة دائمة.**

---

## 16. الخطوة التالية بعد الموافقة

1. مخطط جداول PostgreSQL للمالية (مطابق لجداول: Incomes, Outcomes, Exchanges, Transfers, Advances, Audit, Notifications…).
2. مشروع `uni-gate` فارغ بالهيكل أعلاه.
3. استيراد بيانات TRADIVIA من Google Sheets كأول عميل تجريبي على المنصة.
