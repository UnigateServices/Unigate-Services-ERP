## 1. ما هذا المشروع — وما ليس

### ما هو

| البند | التوضيح |
|-------|---------|
| **الاسم** | TRADIVIA Finance v2 (أو `tradivia-finance-v2`) |
| **العميل** | شركة TRADIVIA — عميل UNI GATE |
| **الهدف** | نقل نظام المالية الحالي من Google Apps Script إلى منصة احترافية حقيقية، ثم توسيعه بميزات مالية متقدمة |
| **المدة** | الوقت كافٍ. الاكتمال والصحة مقدَّمان على سرعة التسليم |
| **النطاق** | شركة واحدة (TRADIVIA) — **ليس** multi-tenant في هذه المرحلة |

### ما ليس

| البند | التوضيح |
|-------|---------|
| **ليس UNI GATE ERP الكامل** | ERP الكامل مشروع منفصل يبنيه الشريك المبرمج خلال ~3 أشهر |
| **ليس نقطة البداية الوحيدة لـ ERP** | الشريك سيبدأ قريباً ببناء **أساس ERP** (هيكل، مصادقة، multi-tenant، وحدات فارغة). أنت تبني **قسم المالية لـ TRADIVIA** بشكل مستقل |
| **ليس نسخة GAS محسّنة** | لا ننقل ملفات `.js` و `.html` كما هي — نعيد كتابة المنطق على NestJS + PostgreSQL |
| **ليس استبدالاً فورياً** | النظام القديم (GAS) يبقى يعمل للعميل حتى اكتمال الاختبار والهجرة |

### العلاقة مع UNI GATE ERP (المستقبل)

```
┌─────────────────────────────┐     ┌─────────────────────────────┐
│  TRADIVIA Finance v2        │     │  UNI GATE ERP (الشريك)      │
│  (أنت — الآن)               │     │  (الشريك — يبدأ قريباً)      │
│                             │     │                             │
│  • عميل واحد: TRADIVIA      │     │  • multi-tenant             │
│  • مالية + فواتير + مستودع  │     │  • هيكل وحدات فارغ          │
│  • NestJS + Next.js + PG    │     │  • finance, exchange, gold  │
└──────────────┬──────────────┘     └──────────────┬──────────────┘
               │                                    │
               └──────────► دمج لاحق ◄──────────────┘
                    قسم المالية يُنقل كوحدة `finance`
                    قسم الصرافة يُنقل كوحدة `exchange`
```

**قاعدة التصميم:** استخدم **نفس المكدس** (TypeScript, NestJS, Next.js, PostgreSQL, Prisma) و**نفس أسماء الجداول والمفاهيم** المخططة لـ ERP، لكن **بدون** `tenant_id` الآن (أو اجعله ثابتاً = `tradivia`). هذا يسهل نقل الكود لاحقاً.

## 1ب. معيار العمل — يسري على كل ما يلي

هذا القسم يعلو على أي عبارة في هذه الوثيقة تتحدث عن أسبوعين، أو MVP، أو «خارج النطاق مؤقتاً»، أو نسخ شكل شاشة قديمة.

1. **الوقت كافٍ.** لا يُختصر سلوك، ولا قاعدة بيانات، ولا واجهة حتى يلحق موعد. الشاشة الناقصة والقائمة المقطوعة عيب يُصلح قبل الانتقال للميزة التالية.
2. **التصميم من مصدر واحد.** القوائم، الجداول، الأزرار، النوافذ، الحقول، والحالات الفارغة مكوّنات مشتركة. الشاشة تستدعيها ولا تعيد رسمها. تعديل شكل القائمة يتم في المكوّن المشترك فيتغيّر في كل الشاشات.
3. **الألوان مؤجَّلة.** تبقى في رموز الهوية (`brand-tokens`) حتى يُستبدل النظام اللوني لاحقاً دفعة واحدة. اكتمال التخطيط والسلوك لا ينتظر لوحة الألوان النهائية.
4. **إعادة البناء مسموحة.** إن بُنيت شاشة أو مسار كقطعة مستقلة، تُعاد على المكوّن المشترك بدل ترقيع كل شاشة.
5. **المحاسبة كاملة.** دليل حسابات، قيد متوازن، ترحيل من العمليات، ميزانية، وقوائم مالية. القيد اليدوي وحده ليس نهاية الميزة. ما يُؤجَّل هو التكامل الحكومي (فاتورة إلكترونية، ضرائب معقّدة) لا أصل القيد والتكلفة والقوائم.

## حالة التنفيذ — 24 أيلول 2026

ما يلي مبني في قاعدة البيانات والخادم والواجهة. الواجهات تعمل، وهي بعدُ شاشات مستقلة وليست مكوّنات تصميم مشتركة. هذا دين جودة، لا يعني أن الميزة غير موجودة.

### منفَّذ

| المجال | ما يعمل |
|--------|---------|
| الدخول والصلاحيات | مدير عام، مشرف، موظف، مراقب. جلسة، قفل شاشة، مكاتب |
| العمليات النقدية | وارد، صادر، تصريف، تحويل، سلف، رصيد افتتاحي. الأرصدة تُحسب ولا تُخزَّن |
| البيانات الأساسية | موظفون، مستلفون، مشاريع، بنوك، مكاتب |
| الرقابة | مراقبة، موافقات تعديل/حذف، إشعارات، سجل تدقيق، تقارير تشغيلية، مرفقات |
| المستودع | مستودعات، أصناف وصور، إدخال وإخراج وجرد. الرصيد من الحركات |
| فواتير البيع | زبون، مسودة، ترحيل يُخرج المخزون، قبض يُنشئ وارداً، إلغاء يعيد الكمية |
| فواتير الشراء | مورد، مسودة، ترحيل يُدخل المخزون ويحدّث متوسط التكلفة، دفع يُنشئ صادراً، إلغاء يُخرج الكمية |

الفواتير والعمليات النقدية **لا تُرحَّل بعد إلى قيد محاسبي**. لا يوجد دليل حسابات ولا ميزانية ولا قائمة أرباح وخسائر.

### نعمله الآن في هذا المشروع

1. مكوّنات واجهة مشتركة: قائمة، جدول، زر، نافذة، حقل. ثم نقل الشاشات الحالية إليها، وإصلاح القصّ في القوائم من المصدر الواحد.
2. دليل حسابات وقيد يومية متوازن (المدين = الدائن).
3. ترحيل تلقائي من الوارد والصادر والتصريف والتحويل والسلف وفواتير البيع والشراء.
4. ميزانية مقابل الفعلي.
5. قائمة أرباح وخسائر وميزانية عمومية.
6. هجرة بيانات TRADIVIA من النظام القديم، ومقارنة الأرصدة، ثم النشر. هذا تسليم العميل وليس ميزة ERP.

### نؤجّله داخل هذا المشروع حتى يثبت الدفتر

- قائمة التدفقات النقدية.
- مراكز تكلفة متعددة.
- طباعة فاتورة بهوية نهائية (السلوك موجود؛ الشكل النهائي مع الألوان).

### نؤجّله لمنصة UNI GATE ERP

- عدة شركات على نفس النظام (multi-tenant).
- فاتورة إلكترونية حكومية وضرائب معقّدة.
- وحدات غير المالية: صرافة كمنتج مستقل، ذهب، طيران.
- باركود وأجهزة مستودع، إن لم يحتجها تشغيل TRADIVIA اليومي.

## 7. قواعد العمل المالية (من النظام القديم — لا تكسرها)

1. **الأرصدة:** تُحسب من مجموع العمليات + الافتتاحي — لا تخزن رصيداً «معدّلاً يدوياً» بدون قيد.
2. **التحويلات الداخلية:** لا تُحسب كربح في التقارير التشغيلية.
3. **السلف:** تتبع منفصل؛ الاسترداد يُسجّل كعملية سلف وليس وارد عادي.
4. **التصريف:** يؤثر على صندوقين/عملتين؛ سعر الصرف يُحفظ مع العملية.
5. **الموافقات:** تعديل/حذف من الموظف = طلب في `audit_trail` حتى يوافق المشرف.
6. **المرجع (REF):** معرف فريد يربط العملية بالمرفقات والإشعارات.
7. **Soft delete:** لا حذف فعلي للعمليات المالية — `status` أو `deleted_at`.
8. **DB Transactions:** أي عملية تؤثر على أكثر من جدول (فاتورة + مخزون + قيد) داخل transaction واحدة.

## 12. التنسيق مع الشريك (ERP)

### ما يشاركه مع الشريك عند الجاهزية

1. ملف `schema.prisma` أو `docs/database-schema.md`
2. قائمة `docs/api-endpoints.md`
3. قرارات التسمية: `companyId` vs `tenantId`
4. مجلد `apps/api/src/finance/` — الكود المصدر للوحدة

### ما يبنيه الشريك في ERP (بالتوازي)

- هيكل monorepo `uni-gate`
- multi-tenant + `tenant_id`
- مصادقة مركزية
- وحدات فارغة: `exchange`, `gold`, ...
- لوحة إدارة الشركات

### عند الدمج

- نسخ/نقل `finance` module
- إضافة `tenant_id` لكل جدول
- توحيد المصادقة
- هجرة بيانات TRADIVIA من قاعدة v2 إلى قاعدة ERP (أو الإبقاء على نفس DB مع tenant)

## 13. إدارة توقعات العميل (TRADIVIA)

**ما تقوله للعميل:**

> «ننقل النظام إلى منصة احترافية وأضيف فواتير ومستودع وقيود وميزانية وتقارير أرباح.  
> هذه نسخة متقدمة ومستقلة — ليست ERP الكامل متعدد الأقسام.  
> ERP الكامل قيد التطوير ويُدمج قسم المالية لاحقاً دون فقدان بياناتكم.»

**ما لا تعد به في 2–3 أسابيع:**

- ERP كامل بكل الأقسام
- محاسبة قانونية معتمدة 100%
- تكامل مع جهات حكومية للفواتير الإلكترونية

## 14. تعليمات لـ Cursor AI

عند العمل على هذا المشروع، اتبع:

1. **اقرأ هذا الملف أولاً** قبل أي تعديل كبير.
2. **المرجع للمنطق:** `docs/reference/legacy-gas/Code.js` — لا تخترع قواعد مالية مختلفة.
3. **اللغة:** واجهة عربية RTL؛ أسماء الجداول والـ API بالإنجليزية.
4. **الأولوية:** المرحلة أ كاملة قبل المرحلة ب.
5. **الأمان:** تحقق من الجلسة/الصلاحية في كل endpoint — لا منطق حساس في Frontend فقط.
6. **المعاملات:** استخدم Prisma `$transaction` لكل عملية متعددة الجداول.
7. **لا multi-tenant معقد** — `companyId = 'tradivia'` يكفي الآن.
8. **لا تعدّل** مشروع GAS القديم من هذا المستودع.
9. **وثّق** كل جدول و endpoint جديد في `docs/`.
10. **اسأل** قبل إضافة مكتبات ثقيلة أو تغيير المكدس.

### أوامر مفيدة لبدء محادثة Cursor

